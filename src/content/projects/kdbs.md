## Problem

애플리케이션은 데이터베이스 위에서 절대 틀리면 안 되는 규칙을 직접 지킵니다. 중복 id가 없어야 하고, 그룹 한도를 넘으면 안 되며, 부모 없는 자식 행이 생기면 안 됩니다. 이런 검사는 서비스마다, 작성자마다 코드로 반복됩니다. 에이전트가 작성하는 코드가 늘어날수록 흩어진 규칙은 지켜질 수도 있고 아닐 수도 있는 확률이 됩니다.

## Approach

규칙을 스키마에 한 번 선언하면 엔진이 강제하도록 OLTP 엔진을 새로 만들었습니다. 범용성을 포기하고 키 기반 읽기·쓰기, 짧은 트랜잭션, 낮은 꼬리 지연에 범위를 좁혔습니다.

- **한 번 발급된 식별자.** 48비트 기본 키는 커밋된 뒤 다른 행을 가리키지 않습니다. 저장된 id가 엉뚱한 행을 가리킬 수 없습니다.
- **그룹 한도 단언.** 어떤 주요 DBMS도 강제하지 않는 SQL-92 `CREATE ASSERTION`을 그룹별 `COUNT(*)` / `SUM` 상한으로 제한해 구현했습니다. 위반하는 쓰기는 O(1) 검사로 실행 전에 거부됩니다.
- **바뀌지 않는 실행 계획.** 모든 문장은 파싱 시점에 단계 체인으로 컴파일되고, 같은 형태의 문장은 언제나 같은 계획으로 실행됩니다.
- **결과를 바꾸지 않는 학습.** 엔진은 반복되는 쿼리의 접근 경로를 기록하고 관찰된 값에 대한 조회 구조를 스스로 만들고 지웁니다. 학습한 구조를 모두 지워도 결과는 같고 속도만 느려지며, 이 불변식은 전용 테스트군으로 검증합니다.
- **선택 가능한 내구성.** 트랜잭션마다 `strict` / `group` / `relaxed`를 고르고, 각 등급의 유실 범위를 명시합니다. WAL, 페이지 체크섬, 풀 페이지 이미지, 마운트 시 복구를 갖췄습니다.
- **코어당 스레드 구조.** 코어마다 C++20 코루틴 리액터를 하나씩 두고, 모든 I/O를 주입 가능한 장치 계층으로 통과시켜 엔진 전체를 결정적 시뮬레이션에서 실행합니다.

## Result

- 2026년 7월부터 커밋 1,800여 건으로 엔진 소스 약 11만 행, 테스트 약 10만 행을 작성했습니다.
- 기본 키, 그룹 한도, 외래 키, 내구성 등급, 고정 실행 계획을 엔진이 보장합니다.
- 장애 경로는 결정적 주입으로 실제로 실행해 검증하고, 구현되지 않은 기능은 구현된 기능과 같은 수준으로 문서에 명시합니다.
